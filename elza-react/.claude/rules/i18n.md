# i18n

All **new** user-facing strings go through `react-intl`. Source strings are Czech (the app's primary UI language); English is a translation.

## Two systems — react-intl (new) vs the legacy `i18n()` helper

The codebase has two i18n systems in parallel:

- **New (use this):** `react-intl` — `defineMessages` + `<FormattedMessage>` / `formatMessage`. Strings live in `lang/translated/` (see pipeline below).
- **Legacy (being phased out):** the `i18n('some.key')` helper (`components/i18n`), which reads a global `messages` object loaded from the flat catalog `public/static/res/js/messages_cs.js`. Still has ~280 call sites and is Czech-only.

Rules:
- **New strings → react-intl only.** Do not add keys to `messages_cs.js` or new `i18n()` call sites.
- Leave existing `i18n()` call sites alone unless the surrounding component is already being migrated — don't do drive-by conversions.
- When a component is migrated to react-intl, its keys move from `messages_cs.js` into `defineMessages` / `lang/translated/`.

## Defining strings

- All new user-facing strings via `react-intl` (`<FormattedMessage>` / `formatMessage`). No hard-coded Czech or English in JSX.
- Use `defineMessages` with a stable `id` and a `defaultMessage` (the Czech source text).
- Placement by scope:
  - **Component-only** — inline `defineMessages` in the `.tsx`. (Most of the codebase does this; acceptable.)
  - **Shared across a feature folder** — a sibling `messages.ts` in that folder (e.g. `node-edit/messages.ts`).
  - **Truly global** (buttons, yes/no, close) — `src/components/shared/lang/messages.ts`, exported as `globalMessages`.
- Start inline; promote to `messages.ts` only when a second consumer appears (same promotion rule as `react.md`).

## Message id convention

- Format: `feature.component.key` in lowerCamel dot-notation (e.g. `userSettings.display.language`). All **new** ids use this notation.
- Ids are globally unique — the dot-prefix is the namespace. Do not rely on file location for uniqueness.
- Legacy ids use snake_case (`node_action_*`, `add_desc_item_form_title`). Do not rename existing ids (they key the translation files). New ids use the dot convention.
- **Never auto-convert an existing id to the dot notation.** Renaming an id drops the old key and its translations on the next merge (see the merge behaviour above), so it is a breaking change, not a cleanup. When you encounter a non-dot id (snake_case, kebab, etc.) while working nearby, leave it as-is and **ask the user** whether they want it migrated. Only rename after they confirm — and then update every reference and re-translate, since the old translations are lost.

## Pluralization

Any message whose text depends on a count must use ICU `plural`, never string concatenation or a ternary. `{count} fondů` is wrong — it reads ungrammatically for 1 and 2–4.

- Syntax: `{count, plural, one {…} few {…} other {…}}`. Use `#` inside a branch to print the number (`{count, plural, one {# fond} …}`).
- **Match the plural categories to the locale, per branch — not to Czech everywhere.** Each locale carries only the CLDR categories it needs:
  - **Czech (`cs`, the `defaultMessage`):** `one` (1), `few` (2–4), `other` (0, 5+). Optionally `many` for decimals.
  - **English (`en`):** `one` (1), `other` (everything else). No `few`.
  - A branch a locale never selects is dead weight; a missing branch falls through to `other`.
- **Mind grammatical case.** The Czech noun form depends on the surrounding preposition, not just the count. After `nad` (instrumental): `one {# fondem} few {# fondy} other {# fondy}`. Standalone/genitive count: `one {# fond} few {# fondy} other {# fondů}`. Pick the form that reads correctly in the sentence.
- **Don't assert the exact rendered plural string in tests** — it couples the test to wording and to CLDR. Match the stable parts (label + the number) with a regex: `screen.getByText(/Pravidla A.*\b2\b/)`, not `'Pravidla A (2 fondy)'`.
- ICU is validated at `locale:compile`; a malformed `plural` block fails the build.

## defaultMessage vs translation files — what to edit where

| Change | Edit | Why |
|--------|------|-----|
| Czech source wording | `defaultMessage` in the component | The component is the single source for Czech. Re-extract propagates it. |
| English wording / fix | `lang/translated/en.json` | English has no source in code; it is a hand-maintained translation. |
| Never edit by hand | `public/static/res/locale/*` | Compiled runtime artifact (gitignored). Overwritten every build. |

- `defaultMessage` **is** the Czech translation (cs is the default locale). Czech changes flow code → extract → cs catalog.
- `lang/translated/` is the source of truth for catalogs and **is committed to git**. `public/static/res/locale/` is generated and gitignored.

## Build pipeline

- **cs is the source and is ephemeral.** `locale:extract` regenerates `lang/translated/cs.json` from the components' `defaultMessage`. It is **gitignored** — never committed, never hand-edited. To change Czech text, edit the `defaultMessage` in the component.
- **en (and future locales) are the committed source of truth** — hand-maintained translation catalogs in `lang/translated/`.
- Runtime = `public/static/res/locale/*.json` (`{id: message}`), generated by `locale:compile`, gitignored, never edited.

**Descriptor fields** (target locales only, e.g. en): `defaultMessage`; optional `translated: false` (untranslated / needs work); `srcHash` (hash of the cs text this entry was translated against). Both `translated` and `srcHash` are stripped by `locale:compile`, so they never ship. cs carries neither.

npm scripts (all `locale:`):
- `locale:extract` — extract → `lang/translated/cs.json` (ephemeral source).
- `locale:merge [-- --source <loc>] <locale...>` — sync catalogs against cs: keep up-to-date translations, seed new keys (`translated: false` + `srcHash`), **re-flag entries whose cs text changed** (srcHash drift → `translated: false`, srcHash bumped), drop stale keys, create missing locale files. `--source cs` marks cs authoritative (no flag/hash). npm needs the `--` separator to forward flags.
- `locale:sync` — `locale:extract` then `locale:merge -- --source cs cs en`. The normal dev entry point.
- `locale:check [-- --source <loc>] <locale...>` — read-only gate; fails on missing/stale keys, `translated: false`, or `srcHash` drift (outdated). Needs cs present (run `locale:extract`/`locale:sync` first).
- `locale:compile` — compile `lang/translated/*` → runtime (strips `translated` + `srcHash`, validates ICU).

Adding/changing a string:
1. Edit/add `defineMessages` in the component (Czech `defaultMessage`).
2. `npm run locale:sync` — regenerate cs + sync en (new/changed keys flagged `translated: false`).
3. Translate the flagged keys in `lang/translated/en.json`, removing `translated: false` as you go (leave `srcHash` — it pins the cs version).
4. `npm run locale:check -- --source cs en` — verify (fail fast before compiling).
5. `npm run locale:compile` — build runtime (also validates ICU).

Removing a string: delete from the component, then `npm run locale:sync` — merge drops the stale key from every catalog.

Reworking Czech text: edit the `defaultMessage`, `locale:sync`. The cs hash changes → merge re-flags the affected en entries `translated: false` (staleness caught automatically), so you can't ship en text that silently no longer matches the Czech.

## Adding a new locale

Two steps, both required — a compiled catalog alone will NOT appear in the UI:
1. `npm run locale:merge -- --source cs cs en <newLocale>` to create `lang/translated/<newLocale>.json`, translate it, `locale:compile`.
2. **Add the locale to `languageOptions` in `components/user/DisplaySettings.tsx`** (`{ value, nativeName }`). The settings language select is driven by that hardcoded list, so a locale missing from it is unreachable even when its catalog exists.

New locale catalogs ARE committed (unlike cs). Only cs is gitignored/ephemeral.

(The hardcoded list is the current manual choke point. A future server-provided locale list would replace it — see the `project_package_locales_option` memory.)

## Corrector workflow (non-developer editing text)

- A non-dev corrector edits catalog files in `lang/translated/`, never source code.
- `locale:merge` **does not clobber** their corrections: it feeds the key set and seeds only new keys; existing human-edited values are preserved.
- `locale:check` flags any `translated: false`, so a new string can't silently ship untranslated. Run it in the CI lint lane (the Maven build auto-merges and would otherwise ship the Czech fallback).

## Maven / CI

- Release (`pom.xml`, generate-sources): `locale:extract` → `locale:merge -- --source cs cs en` → `locale:compile`. (No `locale:check` in the build — merge auto-seeds, so the build must not block on untranslated; check is the separate gate.)
- `locale:check` and `tsc -p tsconfig.scripts.json` belong in the CI lint lane. Note scripts run via node native type-stripping (needs node ≥23.6), which does NOT type-check — so the `tsc` step is the only thing checking script types.
